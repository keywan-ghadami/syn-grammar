# Error Handling Strategy

The parser generated by `syn-grammar` employs a sophisticated error handling strategy designed to provide helpful, context-aware error messages while navigating complex grammar rules. This document explains the key concepts and mechanisms involved.

## Overview

The core of the error handling system is the `ParseContext`, which maintains the state of the parsing process, including the "best" error encountered so far. As the parser attempts different alternatives and traverses rules, it records failures. When the entire parse fails, the `ParseContext` provides the most relevant error to the user.

## Key Concepts

### 1. The "Best" Error

Not all parsing errors are equal. When multiple alternatives fail, we want to report the one that got the "furthest" or was the most specific. The `ParseContext` uses a set of heuristics to determine which error is "better":

1.  **Fatality**: A fatal error (marked with `!`) always takes precedence.
2.  **Progress (Location)**: An error that occurs deeper in the input (further down the line or column) is generally better because it implies a longer successful match prefix.
3.  **Priority**: Errors can be assigned a numeric priority. Higher priority errors win.
    *   **Priority 2**: Triggered by the `fail` keyword.
    *   **Priority 1**: Assigned to labeled alternatives when the failure occurs at the very start of the alternative.
    *   **Priority 0**: Standard parsing errors.
4.  **Context Specificity**:
    *   **Rule Depth**: Errors occurring deeper in the rule stack are preferred.
    *   **Labels**: An error with an explicit label is preferred over one without.
    *   **Message Length**: Longer error messages (presumably containing more information) are used as a tie-breaker.

### 2. Alternatives and Shadowing

When a rule has multiple alternatives (e.g., `A | B | C`), the parser tries them in order.
*   If `A` fails, the parser backtracks and tries `B`.
*   The error from `A` is recorded in the `ParseContext`.
*   If `B` also fails, its error is compared against `A`'s error. The "best" of the two is kept.

**Shadowing** occurs when an earlier alternative fails "better" than a later one. For example, if `A` matches 10 tokens and then fails, while `B` fails at the first token, the error from `A` will likely be reported, "shadowing" the failure of `B`. This is usually desired, as `A` was likely the intended branch.

### 3. Alternatives with Same Length

If two alternatives fail at the exact same position (same progress), the tie-breaking rules (Priority, Context) decide.
*   If one has a **label** (e.g., `rule: "my_label" ...`), it wins (Priority 1).
*   If both are unlabeled, the one deeper in the rule stack wins.
*   If all else is equal, the last recorded one might persist or be decided by message length.

### 4. `fail` Keyword

The `fail` keyword in the grammar allows you to explicitly trigger a high-priority error.
*   It sets a flag in the `ParseContext` that bumps the priority of the *next* recorded error to **2**.
*   This is useful for semantic checks or "panic" modes where you know the input is invalid and want to force a specific error message, overriding potentially "deeper" but irrelevant errors from other branches.

### 5. Labels

You can attach labels to alternatives or symbols to provide friendlier error messages.
*   Syntax: `rule: "expected identifier" Ident;`
*   When a labeled part fails *without consuming any input* (at the start), the error message is transformed to `expected <label>`.
*   This is given **Priority 1**, helping it win against generic "unexpected token" errors at the same location.

### 6. Sequences and Progress

In a sequence `A B C`:
*   If `A` succeeds, the parser commits to `A`.
*   If `B` fails, the error is recorded.
*   Because input was consumed by `A`, this error has "made progress".
*   Errors with progress usually beat errors at the start of the rule.
*   This helps pinpoint the failure: "Matched A, but failed at B".

### 7. Rule Stack Traces

The `ParseContext` tracks the stack of rules currently being parsed.
*   When an error is finalized, the context allows reconstructing the path: `in rule 'Expression': in rule 'Term': expected integer`.
*   This provides valuable context to the user about *where* in the grammar structure the failure occurred.

### 8. The Cut Operator (`=>`)

The cut operator commits the parser to the current alternative if the part before the `=>` succeeds.
*   Syntax: `pattern => action` or `part1 => part2`
*   If `part1` matches successfully, the parser *cuts* off all subsequent alternatives for the current rule.
*   If `part2` then fails, the error is immediately reported as **fatal**, preventing any backtracking to other alternatives.
*   This is crucial for performance and for generating accurate error messages when a prefix unambiguously identifies the correct path.

## Summary of Heuristics

| Heuristic | Condition to Win |
| :--- | :--- |
| **Fatality** | `new.fatal && !old.fatal` |
| **Position** | `new.line > old.line` OR `new.col > old.col` |
| **Priority** | `new.priority > old.priority` |
| **Stack Depth** | `new.stack.len() > old.stack.len()` |
| **Label** | `new.has_label && !old.has_label` |
| **Info** | `new.msg.len() >= old.msg.len()` |
