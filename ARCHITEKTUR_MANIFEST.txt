Architektur- und Status-Manifest: grammar-kit

**1. Projekt-Kontext**

*   **Gesamtziel:** Das `grammar-kit` Framework dient der Erstellung von Zero-Cost Parsern in Rust. Der Kernanspruch ist, die diagnostische Präzision von Compiler-Fehlermeldungen auf ein Maximum zu steigern, ohne dabei Laufzeit-Overhead durch komplexe Zustandsverfolgung zu erzeugen.
*   **Progress Tracking:** Das System misst den Parsing-Fortschritt rein auf Basis des Token-Streams (Zeile und Spalte), entkoppelt von der semantischen Bedeutung der geparsten Regeln. Ein Fehler, der "tiefer" (weiter hinten) im Input auftritt, wird immer als relevanter eingestuft als ein früherer, flacher Fehler.
*   **Fehlerdiagnostik:** Das Ziel ist die Generierung von Fehlermeldungen, die dem Entwickler den exakten, erwarteten Kontext ("expected <item-label>") an der spezifischsten Fehlerstelle liefern, inklusive des vollständigen Regel-Stacks ("in rule_a in rule_b...").

**2. Workspace- und Dateistruktur**

*   **Workspace-Struktur:** Das Projekt ist ein Cargo Workspace mit zwei primären Crates: `core/grammar-kit` und `syn-grammar`.

*   **Core Runtime (`core/grammar-kit`):**
    *   `core/grammar-kit/src/lib.rs`: **Die Engine.** Beinhaltet die gesamte Laufzeitlogik für das zustandsbehaftete Parsen. Die Schlüsselkomponenten `ParseContext`, `attempt_labeled`, `record_error` und die Kombinatoren (`parse_separated`) sind hier definiert. Dies ist der primäre Ort für die Implementierung der Fehlerdiagnose-Heuristiken.
    *   `core/grammar-kit/src/testing.rs`: **Das Test-Framework.** Definiert die `Testable` Trait und `TestResult` Struktur, die eine fluente API zur Verfügung stellen, um Parser-Ergebnisse zu validieren (`assert_failure_contains`, etc.). Fehler in den Tests paniken oft aus diesem File heraus.

*   **Makro und Grammatik-Definition (`syn-grammar`):**
    *   `syn-grammar/Cargo.toml`: Definiert den Workspace und die Abhängigkeiten der `syn-grammar`-Crate.
    *   `syn-grammar/syn-grammar-macros/`: Das Verzeichnis für die prozedurale Makro-Crate.
        *   `syn-grammar/syn-grammar-macros/src/lib.rs`: **Der Makro-Einstiegspunkt.** Definiert das `#[proc_macro]` `grammar!`. Leitet die Token zur Verarbeitung an `codegen` weiter.
        *   `syn-grammar/syn-grammar-macros/src/codegen/mod.rs`: **Der Code-Generator.** Hauptmodul für die Umwandlung der abstrakten Grammatik-Definition in konkreten Rust-Parser-Code.
        *   `syn-grammar/syn-grammar-macros/src/codegen/rule.rs` & `pattern.rs`: **Die Generierungslogik.** Diese Module enthalten die Logik, um aus den Grammatikregeln (`rule`) und deren Mustern (`pattern`) die Aufrufe an die `grammar-kit`-Laufzeit (`attempt_labeled`, `parse_separated`, etc.) zu generieren. Hier wird die Brücke zwischen der definierten Grammatik und der Laufzeit-Engine geschlagen.
    *   `syn-grammar/tests/`: Das Verzeichnis, das alle Integrationstests enthält.
        *   `syn-grammar/tests/list_dx_test.rs`: **Das aktuelle Test-Szenario.** Dieser Test validiert die Qualität der Fehlermeldungen bei komplexen Listen-Strukturen und war der Fokus der letzten Korrekturen.

*   **Feature-Flags:**
    *   `rt` (runtime): Zwingend notwendig. Aktiviert `ParseContext` und die gesamte zustandsbehaftete Parsing-Logik in `core/grammar-kit`.
    *   `syn`: Zwingend notwendig. Stellt die Integration mit der `syn`-Crate bereit, um auf deren Typen (`ParseStream`, `Error`) aufzubauen.

**3. Funktionsarchitektur & Zusammenhänge (ParseContext)**

*   **`attempt_labeled`:** Bildet eine spekulative Transaktionsgrenze.
    *   **Erfolg:** Der Input-Stream wird vorgerückt.
    *   **Fehler:** Der Input-Stream wird zurückgesetzt. Die Fehlerbehandlung ist kritisch und zweigeteilt:
        *   **Deep Failure (Fortschritt > 0 Tokens):** Der im `ParseContext` bereits von einer tieferen Regel erfasste, spezifische Fehler wird beibehalten. `attempt_labeled` selbst verändert den `best_error` Zustand in diesem Fall NICHT, um die hoch-spezifische Meldung zu schützen.
        *   **Shallow Failure (Fortschritt == 0 Tokens):** Dies signalisiert das Scheitern einer Alternative an ihrer Grenze. Ein *Error Snapshot* wird wiederhergestellt (der Fehlerzustand von *vor* dem Versuch wird reaktiviert), und *danach* wird ein neuer, gelabelter Fehler mit `PRIO_LABELED` aufgezeichnet. Dies verhindert, dass interne Implementierungsdetails des gescheiterten Zweigs als "bester" Fehler nach außen dringen.
*   **`record_error`:** Die zentrale Schiedsrichterfunktion für Fehler, die entscheidet, welcher Fehler der "beste" ist.
    *   **Dominanz der Position:** Ein neuer Fehler überschreibt einen alten Fehler *immer*, wenn seine Startposition (Zeile, dann Spalte) weiter im Input liegt. Dies ist die absolute Priorität #1.
    *   **Tie-Breaker-Logik (bei gleicher Position):**
        1.  **Fatalität:** Ein fataler Fehler (`is_fatal`) gewinnt immer gegen einen nicht-fatalen.
        2.  **Priorität (u8):** Ein Fehler mit höherer Prioritäts-Konstante (z.B. `PRIO_STRUCTURAL`, `PRIO_LABELED`) gewinnt.
        3.  **Kontext-Spezifität:** Ein Fehler mit tieferem Regel-Stack oder einem expliziten Label gewinnt gegen einen ohne.
        4.  **Nachrichtenlänge:** Als letzter Tie-Breaker gewinnt die längere (informativere) Fehlermeldung.
*   **`stop_aggregation`:** Ein Schutzmechanismus. Er verhindert, dass ein hoch-relevanter, tiefer Fehler (z.B. "expected identifier at column 35") von einem späteren, aber generischeren Fehler einer übergeordneten Regel (z.B. "expected item") überschrieben wird. Er stoppt die Fehlersuche in alternativen Zweigen, wenn ein "guter" Fehler (fatal, hohe Priorität oder tief im Input) bereits gefunden wurde.
*   **`parse_separated`:** Kombinator für Listen.
    *   **Entkopplung:** Nutzt `attempt_labeled` für jedes Item und `attempt` für den Separator. Wenn die Separator-Analyse fehlschlägt, wird nur der Zustand *nach* dem letzten erfolgreichen Item wiederhergestellt. Der Fehler für ein fehlendes Item *nach* einem Komma wird jedoch als harter, nicht wiederherstellbarer Fehler behandelt, da die Grammatik hier eindeutig ist und ein Item erwartet werden muss.

**4. Aktueller Aufgabenstatus**

*   **Problemstellung:** Das "Dangling Comma"-Szenario (`fn foo( int a, );`) wurde falsch diagnostiziert. Der Parser erwartete ein weiteres `function parameter` nach dem Komma. Da der Input am Ende war, schlug der Versuch, ein Item zu parsen, bei Spalte 15 (dem Start des Versuchs) fehl.
*   **Ursprünglicher Architekturfehler:** Der `attempt_labeled`-Aufruf für das nicht gefundene Item meldete korrekterweise einen Shallow Failure (0 Token Fortschritt). Die vorherige Implementierung behandelte diesen Fehler jedoch fälschlicherweise als "tief", weil der *gesamte* `parse_separated`-Aufruf bereits Fortschritt gemacht hatte (durch das Parsen von "int a,"). Dadurch wurde der spezifische, hoch-priorisierte Fehler "unexpected end of input, expected function parameter" durch eine generische, irrelevante Meldung aus einem alternativen Zweig überschrieben.
*   **Implementierte Lösung:** Die Logik in `attempt_labeled` wurde final korrigiert. Sie unterscheidet jetzt strikt basierend auf dem Fortschritt *innerhalb des Blocks*:
    *   **Fortschritt im Block == 0 Tokens:** Es wird ein Hard-Reset des `best_error` auf den Snapshot von *vor* dem Versuch durchgeführt. Das löscht alle "inneren" Fehler des fehlgeschlagenen Zweigs und stellt sicher, dass das äußere Label ("expected function parameter") zur dominanten, hoch-priorisierten Fehlermeldung wird.
    *   **Fortschritt im Block > 0 Tokens:** Der `best_error` wird *nicht* angetastet, um den bereits aufgezeichneten tiefen, spezifischen Fehler zu bewahren.
*   **Finaler Zustand:** Das System ist nun in der Lage, sowohl tiefe Fehler innerhalb von Strukturen als auch flache Fehler an den Grenzen von Alternativen korrekt und mit der maximalen Spezifität zu diagnostizieren. Die Logik im Kern (`core/grammar-kit/src/lib.rs`) ist stabil. Der nächste und letzte Schritt ist die Aktualisierung der Test-Assertions in `syn-grammar/tests/list_dx_test.rs` auf die korrekten, neuen Fehlermeldungen, um den Entwicklungszyklus abzuschließen.
